# 当前调度算法

2026-10-24，按src/core/planner.ts、src/dispatcher/scheduler.ts与harness/adapter.mjs描述实际实现。

当前算法是**依赖与资源约束下的贪心列表调度，加连续任务链融合**。完成事件驱动实际推进；不预测LLM工期，不使用HEFT，也不承诺全局最优。

## 1. 找到真正就绪的任务

先诊断缺失前置、未知产物和依赖环。任务只有在pending、已授权、硬前置满足且资源可用时进入就绪集；暂停时不启动新任务。

任务依赖要求上游completed；产物依赖要求对应output已accepted。只使用实际状态，不把未来计划算作交付。资源按项目相对文件/目录匹配，读读可并行，写入与重叠读写互斥；未结束或unknown运行仍保留占用。这是协作声明，不是文件系统隔离。

## 2. 排序并贪心分配

就绪任务按以下顺序比较：

1. priority数值越小越先。
2. 同优先级时，依赖图上可达的全部后代任务越多越先。
3. 再按ID的localeCompare顺序兜底。

后代数量是图结构指标，包含间接后继；不是“本次立即能解锁的数量”，也不是关键路径长度、预计耗时或动态未完成后继数。当前实现没有计算这几类指标。

全局规划按agents配置顺序，为空闲成员选择第一个owner/category匹配、未被预留、与已选首任务无资源冲突的就绪任务。实际dispatch/next则针对指定成员重新规划，其他成员的建议不会占走该成员可做的任务。没有额外的上下文成本、速度或负载均衡模型。

## 3. 沿连续依赖链融合执行段

从选中的首项开始，在虚拟状态中推演它已完成，再找同一个成员能承担、直接依赖上一项且此时就绪的后续任务。分支按priority、ID选择，不再使用后代数量排序。

遇到review检查点、没有满足条件的可接续项，或maxSegment上限时停止。默认maxSegment为4。类别本身不是执行段边界；跨成员消费者被记录为中间交付点，交付可解锁其他成员，原成员仍可继续自己的链。

例如A1→A2→等待B3→A3→A4：B3未交付时，A的建议段只包含A1、A2；交付后再计算后续。虚拟完成只用于建议，不改变实际状态，也不预先锁住未来任务。当前贪心延伸不保证找到最长链或全局最佳划分。

## 4. 按真实事件逐项执行

dispatch仅启动并占用当前一项，segment后续项是建议；成员完成后再next，重新检查真实前置与资源。report交付以及accept、approve、resume等管理动作会触发自动派发检查。

开启autoDispatch时，已登记waiting的成员若有任务就收到消息；DSH可恢复已自然卸载成员的原Session。当前成员若仍在回合内，可自行next连续领取。没有持续模型轮询或后台定时调度。

当前每次plan都会重新诊断、扫描、排序并构造执行段，**尚未实现局部增量重算**。事件驱动不等于增量算法。未知投递不自动重发，失败不自动重试。

## 5. 证据与适用范围

七组合成图四种策略共28次运行均完成、0约束违规，不同策略各有胜负。worklist-03真实九任务完成、两轮123/123，Lead手动dispatch0、六次消息唤醒、两次连续领取；四段前置齐备到dispatch为4.954秒。具体见[评审](worklist-03评审.md)。

这些结果支持当前小任务图的可解释调度与自动推进，不证明全局最优、长期成本下降或上下文压缩减少。实现入口见[planner.ts](../src/core/planner.ts)、[scheduler.ts](../src/dispatcher/scheduler.ts)、[adapter.mjs](../harness/adapter.mjs)。
