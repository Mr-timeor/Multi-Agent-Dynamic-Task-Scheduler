# 快速开始

本指南面向第一次使用插件的开发者。当前Harness集成在Windows / Desktop 0.2.1-rc.2验证；纯本地规划与图导出无需Harness。

## 1. 获取源码并构建

需要Node.js 22+、npm，以及已配置可用模型的DeepSeek Harness。

```sh
git clone https://github.com/Mr-timeor/Multi-Agent-Dynamic-Task-Scheduler.git
cd Multi-Agent-Dynamic-Task-Scheduler
npm ci
npm run build
npm run build:view
```

`build`生成调度器bundle；`build:view`生成可选只读图bundle。运行时依赖的Harness包由宿主提供。当前采用本地bundle安装，没有npm一键安装入口。

仅预览算法与图时，可用 `npm run demo`，浏览器打开 `.scheduler/flow.html`，无需执行后续步骤。

## 2. 准备目标项目

在要开发的仓库中创建：

```text
my-app/
  .scheduler/
    tasks.json       # 输入：任务、执行者、依赖和资源
    task-cards.md    # 输入：每项要求、交付物和验收方式
    state.json       # 首次调用插件时自动创建
    flow.html        # 只读图插件自动导出
```

从[开发测试模板](../fixtures/development.json)复制得到tasks.json，并替换成实际需求。任务标题应包含具体要求或指向任务卡，例如“按 .scheduler/task-cards.md 的A2实现接口”。专项成员按领取到的当前任务工作，不会自动获得Lead的完整对话。

模板中developer负责接口、实现和文档，tester负责独立测试与联合回归。联合回归设有 `review:true`，由Lead检查实际测试证据后验收。

- `dependsOn`：上游任务完成，或指定产物被接受后才能开始。
- `resources`：项目相对路径；读读允许并行，重叠读写/写写互斥。
- `outputs`：要交付的产物名称，提交时提供文件或其他引用。
- `owner`、`category`：匹配声明的专项成员与能力类别。

字段详情见[接口与数据格式](接口与数据契约.md)。文件互斥是协作约定，成员实际修改范围仍由任务卡约束。

首次运行使用一个新的stateFile。已有状态会继续原任务，不会因改tasks.json而自动重载；不要清空或手改正在执行的state。

## 3. 安装bundle并配置profile

通过Harness的 `plugin_manager` / `install_bundle` 安装源码目录中的 `harness/bundle`。需要图时，再安装 `harness/view-bundle`。

bundle应由profile管理，不要直接用profile外的绝对file://入口替代安装，这会影响宿主依赖解析。

在所用profile的 `cordis.patch.yml` 配置agent-team服务，并按既有插件id启用bundle。下面的 `D:/projects/my-app` 是示例路径，需替换为目标仓库的绝对路径。

```yaml
- insert:
    - id: agent-team
      name: '@deepseek-ai/dsh-experimental-agent-team'
      config:
        maxMembers: 8
        maxTasks: 256
        maxMessageBytes: 65536
        disposalTimeoutMs: 5000
- id: dynamic-task-scheduler
  disabled: false
  config:
    leadSessionId: auto
    autoDispatch: true
    projectFile: 'D:/projects/my-app/.scheduler/tasks.json'
    stateFile: 'D:/projects/my-app/.scheduler/state.json'
- id: dynamic-task-scheduler-view
  disabled: false
  config:
    projectFile: 'D:/projects/my-app/.scheduler/tasks.json'
    stateFile: 'D:/projects/my-app/.scheduler/state.json'
    graphFile: 'D:/projects/my-app/.scheduler/flow.html'
```

已有agent-team服务时保留现有服务，不重复插入。仅需成员/消息服务，不必启用原生任务板工具。不安装图bundle时省略view配置。

覆盖两个bundle配置时只写id、启用设置与config，不再写name。修改前保存原profile配置，完整退出并重启Harness后使用。

## 4. 新建一个Lead会话

工作区应是目标项目目录。第一次合法调度工具调用会绑定Lead，其他会话不要提前调用工具。换Lead或切项目需要重启并重新绑定。

沿用模板中的成员名时，可以给Lead发送：

```text
你是本项目的调度Lead。
读取 .scheduler/tasks.json 和 .scheduler/task-cards.md。
调用scheduler_status，核对初始任务、就绪项和autoDispatch:true。
依次创建tester、developer两个专项成员；常规阶段不手动dispatch。
成员只执行当前任务，提交实际检查依据和产物引用，再next继续。
waiting时结束回合，依赖解除后由插件发送委托唤醒。
需要review的任务，检查测试证据后再accept。
出现失败或unknown时先核对现场，不盲目重发。
完成后汇总交付物、真实测试结果和未解决问题。
```

成员名必须与tasks.json中的agents一致。使用不同成员时相应修改提示。

Lead创建成员的工具调用为：

```text
scheduler_manage({action:"spawn", target:"tester"})
scheduler_manage({action:"spawn", target:"developer"})
```

这些是Harness聊天工具调用，不是终端命令。开启autoDispatch后，成员首次next可直接领取就绪任务；报告完成后next连续领取，或在waiting结束回合后由插件唤醒。

模板的B2进入review后，Lead核对真实回归结果，再调用 `scheduler_manage({action:"accept", target:"B2"})`，才会解锁后续文档任务。普通任务不要求逐项人工审批。

## 5. 查看进度与结束运行

在Harness文件预览打开 `.scheduler/flow.html`。图插件随状态文件变化自动导出；宿主开启HTML交互预览后可以搜索、缩放和查看详情。图只读，不能拖动修改任务。

Lead通过status查看必要进度，不持续轮询；日常派发由成员交付事件驱动。普通completed按成员报告接受，插件不会代替测试执行器或独立检查代码质量，因此任务卡应明确要求保存命令、退出码与输出。

出现unknown或宿主中断时，由Lead核对成员是否仍在执行，再决定继续原运行或结束对账；不自动重发。重启不保留内存waiting登记，不能依赖关机后自动恢复全部流程。

任务完成后保留state、产物和测试证据。切换项目时，先确认原成员停止，再更换两个插件的项目/状态路径并重启；恢复原项目时使用之前保存的配置，不覆盖其他profile设置。

## 离线命令

从插件源码目录执行：

```sh
node dist/cli.js plan path/to/tasks.json
node dist/cli.js graph path/to/tasks.json .scheduler/plan.html
node dist/cli.js status path/to/state.json
node dist/cli.js export path/to/state.json .scheduler/current.html
```

plan/graph从任务定义生成初始方案；status/export读取已有执行状态。图导出与离线查询不会运行Agent或推进业务任务。
