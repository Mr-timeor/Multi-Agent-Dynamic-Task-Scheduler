# 离线合成评测

2026-10-21。实现位于 `src/benchmark/`，输入为 `fixtures/benchmarks/` 的七个 JSON 场景。定向检查 8 项通过；四种策略在七个场景的 28 次模拟中全部交付、违规为 0。这些是可复现的合成结果，不是实际开发或模型效果。

## 运行

在项目根目录运行；编译只更新项目 `dist`，不复制或安装 Harness bundle：

```powershell
node node_modules/typescript/bin/tsc
node --test tests/benchmark.test.mjs
node dist/benchmark/run.js
node dist/benchmark/run.js --zero-overhead
node dist/benchmark/run.js --json
```

CLI 默认输出完整指标表，`--json` 额外给出每次启动、交付、验收、失败和重试的时间轨迹。也可在命令后提供另一场景目录。CLI 不写任务状态；未完成或出现违规时退出码为 1。

## 比较方法

所有策略共用一个事件执行器。输入中的耗时是本次合成执行实际经过的时间，选择器拿不到它们，也不会把 `plan` 的虚拟完成写成事实。依赖只能由完成或产物验收事件解锁。

| 策略 | 选择与分组 |
|---|---|
| 当前执行段策略 | 直接调用核心 `plan`；当前执行段内下一项实际就绪后连续领取，发生阻断后重新规划 |
| 逐任务派发 | 同样调用 `plan`，但段长设为 1；保留相同的优先级和解锁排序，以分离融合效果 |
| 按类别整包 | 输入稳定拓扑顺序中选择就绪任务，同类别保持一个委托批次；受相同段长上限约束 |
| 仅拓扑排序 | 依输入顺序做稳定拓扑排序，逐项派发；不计算下游解锁价值 |

类别整包可以在外部前置期间保留批次，但不占用未来任务的资源；若同一执行者有另一类别可执行，则让出并切换。所有策略都在指定时间发布中间产物，使用相同验收延迟，不等整包完成。每次失败均结束当前批次，按同一重试延迟重新派发。

每名执行者容量为 1，职责与现有负责人来自任务输入。新委托及连续领取的开销均占用执行者和当前任务资源；任务结束后释放资源。读写冲突复用核心的目录/文件规则。授权时间、失败次数、失败耗时、重试延迟、检查点和验收延迟对四种策略完全一致。

默认新委托开销 1、连续领取 0.1，单位为合成分钟。这两个值是实验参数，尚未从 DSH 测量。`--zero-overhead` 同时置零，便于分辨排序与开销假设带来的差异。所有逐项领取仍计数，不能用融合隐去原子任务。

## 指标

| 字段 | 口径 |
|---|---|
| makespan | 所有任务完成验收时的总时长；存在未完成任务时为 null，不计成 0 |
| idle | 全部执行者没有当前任务的时间之和 |
| blocked | idle 的子集：该执行者仍有职责匹配的未完成工作，但此刻不能启动；包含依赖、授权、资源及验收等待 |
| dispatches / claims | 新委托批次 / 实际启动的原子任务次数，失败重试也计数 |
| handoffs | 依赖第一次被消费时，上游与下游执行者不同的边数；按任务/产物引用去重 |
| deliveries / outputDeliveries | 最终验收的任务数 / 唯一已接受产物数；中间产物不在任务完成时重复计数 |
| failures / rework | 失败尝试次数 / 所有失败尝试的工作时间；派发开销另计，不吞掉失败 |
| violations | 启动时检查加独立轨迹审计发现的未授权、提前消费、执行者容量和资源重叠 |

容量对账：`work + overhead + idle = elapsed × 执行者数`。`blocked` 已包含在 `idle` 内，不重复相加。handoffs 是依赖边计数，dispatches 是合成开销单位，都不等于真实消息数或模型请求数。

## 本次结果

同一组默认参数下的总时长：

| 场景 | 执行段 | 逐任务 | 类别整包 | 拓扑排序 |
|---|---:|---:|---:|---:|
| 串行链 | 10.2 | 12 | 10.2 | 12 |
| 分叉汇合 | 11.1 | 12 | 10.2 | 12 |
| 跨类别往返 | 17.1 | 18 | 15.3 | 18 |
| 共享文件与独立工作 | 11 | 11 | 9.2 | 11 |
| 中间接口先交付 | 12 | 12 | 11.1 | 12 |
| 授权与失败重试 | 18 | 18 | 17.1 | 18 |
| 先解锁另一执行者 | 12 | 12 | 17.2 | 19 |

执行段策略没有在全部场景获胜。类别整包能在外部等待期间复用上下文，部分场景因此更省委托开销；保留这一优势，不能故意延后它的中间交付来制造比较结果。

把开销同时置零后，前六个场景四种策略总时长分别一致，串行链均为 9；“先解锁另一执行者”场景中，执行段/逐任务为 9、类别/拓扑为 15。这说明该场景的差异来自下游解锁排序，串行链的差异来自设定的委托开销。

中间接口场景四种策略均在第 4 分钟验收接口并启动测试，早于开发第 9 分钟结束。授权失败场景四种策略均保留 1 次失败、2 分钟返工和 4 次原子任务启动。

## 范围

此处复用当前 `plan` 的选择结果，测量的是规划策略加批次开销模型。当前 Harness 适配器还允许 `scheduler_next` 在首项之后自行领取其他就绪任务；它的消息唤醒、领取及真实请求成本需要单独观测，不能直接套用这里的批次数。

首版固定耗时与失败序列，不估算 LLM 随机时长；验收用固定延迟事件，不模拟审阅者容量；返工仅统计失败尝试，不模拟已交付产物被撤销后的传播返工。失败同时提前交付的输入会明确拒绝。动态新增任务、上下文污染、Token、费用、记忆压缩和真实宿主消息都不在本次合成结论中。
