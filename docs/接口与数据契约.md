# 接口与数据契约

2026-10-20，首版实际接口。以代码为准，不再保留未实现的发布协议、commandId、expectedRevision 或独立许可服务。

## 输入与默认值

任务需要 `id`；执行者需要 `id`。完整例子见 `fixtures/development.json`。

| 字段 | 用法／默认 |
|---|---|
| title、category | 默认任务ID、general |
| dependsOn | 默认空；字符串表示任务完成前置，`{taskId, output}` 表示产物交付前置 |
| resources | 默认空；相对路径字符串表示写入，也可指定 `{path, mode: read或write}` |
| outputs | 要交付的产物名称，默认空；提交时给文件、提交或接口引用 |
| priority | 默认2，越小越优先 |
| owner | 可选，限定执行者 |
| review、approval | 默认false；分别表示交付后验收、启动前授权 |
| agents[].categories | 默认空表示通用执行者 |
| maxSegment | 默认4；执行段任务数量上限 |

首版仅支持任务／产物硬前置。不把软关系、模拟输入或预计完成自动转换成可用结果；扩展输入语义后置。耗时不参与当前算法，无需填写。

## 程序接口

| 接口 | 作用 |
|---|---|
| normalize、diagnose、plan | 规范化、图诊断、就绪集合与执行段；不修改事实 |
| FileStore.open、snapshot、change、close | 单进程串行保存JSON，保留上一版 `.bak` |
| Scheduler.dispatch(agentId, send) | 保存当前任务占用和委托，再调用传输函数一次 |
| acknowledge(agentId, ids) | 确认对应运行；重复回执不增加运行记录 |
| report(agentId, ids, report) | checkpoint、completed、blocked、failed与摘要、产物引用 |
| accept(taskId, output?) | 接受指定中间产物或整项待验收任务 |
| control(action, taskId?) | pause、resume、approve、retry、resolve-stopped |
| addTasks(tasks) | 校验后追加新任务，不修改已执行任务 |
| expire(now?) | 将超过回执等待时间的委托标为unknown |
| renderGraph(state) | 输出只读HTML/SVG快照 |

`dispatchId / attemptId / permitId` 由程序生成并放进同一个Run。它们不是三个审批流程。模型只需传 `dispatchId`，适配器补齐内部回执关联。

## 状态与交付

任务状态：pending、running、review、completed、blocked、failed。Run另记 awaiting、active、unknown、finished。running表示任务已被占用；显示时进一步区分待回执、执行中、待对账。

普通任务按执行者报告接受，摘要应写明检查依据；这不意味着系统验证了测试命令。仅 `review: true` 等待Lead验收。中间产物可独立提交／验收，下游无需等待整个任务完成。

暂停只停止新任务；执行者提交blocked或failed表示本轮工作已停止，释放占用。失联／未知不自动释放，Lead确认停止后使用resolve-stopped。失败后retry创建新运行且保留旧记录；已经接受的产物不自动撤销，有修订时新增任务。

## 宿主工具

- `scheduler_status()`：紧凑状态与方案。
- `scheduler_next(dispatchId?)`：收到委托时确认；当前项结束后空参领取下一项并同时确认。
- `scheduler_report(dispatchId, summary, status?, outputs?)`：默认completed；outputs为产物引用JSON。
- `scheduler_manage(action, target?, output?)`：仅Lead，可创建专项成员、派发、验收、授权、暂停和对账。

由 `exec.agent` 取得身份，只允许配置的Lead团队。工具不调用原生任务板，不要求模型手填身份、版本或资源锁。

## 可选自动派发（020已验收）

Harness配置autoDispatch默认false，开启后成员首次next可领取就绪任务；next无任务时按持久成员name/id登记等待。真实report提交和accept/approve/resume等管理动作后，插件按既有依赖及占用给等待成员派发。report/manage返回wakeups摘要，status增加autoDispatch、waitingAgents（live）和inactiveWaitingAgents（已卸载逻辑等待），原四工具数量不变。成员卸载不删除等待意图；通过原生消息恢复同一Session，不自动spawn替代成员。持久成员失败/缺项由Lead处理。传输失败保留unknown，不撤销上游完成、不重发。

Scheduler.plan(agentId?)支持仅规划指定成员；dispatch在串行状态提交中对指定成员重新检查前置、能力、授权及资源，不让其他空闲成员的建议预留任务。等待集合仅在进程内，不增加持久状态字段，重启后需重新next或手动派发。Desktop 0.2.1-rc.2的隔离Wake、worklist-03真实试用及配置恢复重启确认均通过，020已关闭，见[worklist-03评审](worklist-03评审.md)。

## 必要边界

状态写入成功后才投递；发送未知不重发。回执阈值默认120秒，发送响应有超时计时；回执超时在查询／领取时检查，不另起后台服务。重启时未结束运行进入unknown。

单项目只支持一个写进程；同进程重复打开拒绝。路径占用只是合作约定，不拦截实际文件操作。JSON不承诺断电事务保证。Lead日志替代存储仍是研究选项。

## 用量与防循环（2026-10-22）

请求数、token、费用和总时长只作记录，不设预算上限，不据此阻止派发或判定任务失败。拿不到的用量记unknown。

保留DAG循环诊断、完成运行不可重做、unknown不自动重发和失败后显式retry。next返回waiting后执行者结束本回合，Lead不轮询空等；同一操作没有新信息或状态变化时停止重复，报告阻断，等新交付或明确调整后继续。

其中“不重复空等”是执行说明中的行为规则，当前没有通用的模型调用循环自动检测器。回执超时用于标记失联委托，maxSegment用于划分执行段，均不作为预算限制。
