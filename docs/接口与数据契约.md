# 接口与数据契约

版本：0.2 草案。日期：2026-10-20。本文定义业务语义，不是可调用 API、代码或已冻结的 JSON Schema。名称用于设计沟通；宿主方法需适配。

## 1 通用约定

- 核心接收 JSON 可表达的数据，不含宿主 live Agent、模型 SDK 或 UI 对象。
- 标识均为项目内稳定 ID；Task ID 不等于原生 task ID，Executor ID 不等于 session ID。
- 时间戳采用带时区的 ISO 8601；耗时单位为毫秒，消息大小为 UTF-8 字节，费用附币种。
- 未知值用 null 加 unknownReason 表达，不以 0、空串或猜测值代替。
- 快照包含 schemaVersion、projectId、revision、policyVersion、updatedAt。全局 revision 单调递增。
- 所有写命令包含 commandId、expectedRevision、actor、scope、payload；发布和接管还含 coordinatorEpoch。
- actor 与角色由可信调用上下文解析，不能相信执行者在 JSON 中自报的“人类／验收者”身份。
- commandId 同键同内容返回原结果，同键不同内容报冲突；幂等记录与业务结果一起持久化。
- 业务错误返回 code、message、currentRevision、details、suggestedAction，不以空计划冒充成功。

## 2 输入输出对象

### 2.1 任务图输入

| 对象 | 最小字段 | 语义 |
|---|---|---|
| Project | projectId、schemaVersion、policyVersion、tasks、dependencies、executors、resources | 规划边界；不从其他项目自动取数据 |
| Task | id、title、category、inputs、outputs、acceptancePolicyId、capabilities、resourceNeeds、authorizationNeeds、estimate、risk | 输入输出指明版本要求；估计可未知 |
| Dependency | id、from、to、relation、requiredArtifact、inputMode | relation 为 hard／soft／interface／mock；interface 和 mock 必须明确是否阻塞及替代条件 |
| Executor | id、role、capabilities、contextRef、availability、capacity、contextEstimate | 核心身份和能力；宿主绑定另存 |
| Resource | id、kind、canonicalKey、policy | 文件、目录、数据库等；冲突规则明确且可解释 |
| AcceptancePolicy | id、revision、criteria、reviewerRoles、selfReviewAllowed、evidenceRequirements | 规则不能为空；自验收须显式允许 |
| Authorization | id、issuer、actions、resourceScope、limit、expiresAt、status | 授权与普通任务指令分离 |
| SchedulingPolicy | id、version、limits、ranking、unknownHandling、seed | 段长、并发、预算、计分和平局规则 |

硬边通常引用某个产物的有效验收，也可明确要求整个前置任务验收；不得只写“已完成”而不说明范围。模拟输入的允许范围必须附在消费者任务上，真实联调不得隐式使用 mock。

### 2.2 运行状态

| 对象 | 必备语义 |
|---|---|
| TaskRecord | taskId、lifecycle、currentAttemptId、inputVersions、effectiveVerdicts、blockedReasons；ready 是派生结果 |
| Artifact | id、taskId、attemptId、version、location、digest、inputVersions、status；摘要和证据引用分开 |
| Segment | id、planId、executorId、orderedTaskIds、entryConditions、checkpoints、stopConditions、nextUnlockConditions、limits |
| Attempt | id、taskId、executorId、segmentId、inputVersions、permitId、status、start/end、usage、failure、retryOf |
| Verdict | id、subjectRef、attemptId、artifactVersions、policyRevision、reviewer、decision、evidenceRefs、time |
| ResourceClaim | id、resourceId、mode、attemptId、permitId、ownerEpoch、status、lastConfirmedAt |
| Permit | id、taskId、attemptId、executorId、inputVersions、resourceClaimIds、authorizationRefs、epoch、status |
| DispatchRecord | id、attemptId、messageId、payloadDigest、status、hostReceipt、lastObservedAt |
| Coordinator | activePublisher、epoch、status；第二调度对话默认只有审阅权 |
| HistoryEvent | id、projectRevision、type、actor、subject、attemptId、payload、causationId、timestamp |

状态、历史、许可和待投递记录不能分别提交而留下不一致窗口。具体事务机制在实现前选择。

### 2.3 计划输出

Plan 包含 planId、basedOnRevision、policyVersion、diagnostics、rankedTasks、segments、forecast、unassigned、explanations、assumptions。

- diagnostics 给出循环路径、缺失前置、不可能满足的约束和受影响 ID。
- rankedTasks 给出排序分项和估计依据，不只给总分。
- segments 明确内部任务顺序、建议执行者、中间交付、停止与解锁条件。
- forecast 是预测，不写回实际状态；即使预测依赖会完成，也不发执行许可。
- unassigned 指明依赖、能力、资源、授权、容量或未知输入等具体原因。
- 基于旧 revision 的计划发布前必须重新验证；冲突返回 STALE_PLAN，不自动覆盖。

## 3 状态与解锁规则

任务 lifecycle：

| 转换 | 触发及条件 |
|---|---|
| pending → running | startTask 校验通过并持久化许可；宿主未确认开始时 attempt 单独标为 starting，UI 不显示已在运行 |
| running → submitted | 提交绑定当前 attempt 和输入版本的产物 |
| submitted → accepted | 满足规则的验收者接受全部必需输出 |
| running／submitted → failed | 执行失败或验收拒绝；保留失败原因 |
| failed → pending | 显式授权重试；新 attempt，累计计数不清零 |
| accepted → invalidated | 输入、产物或验收条件失效；保留原 verdict，关联影响范围 |
| invalidated → pending | 形成明确复核或修复安排；不得自动重新启动 |
| 非终态 → cancelled | 未启动可直接取消；已启动须确认停止，否则保留 cancel_requested 和资源 |

上述 running 表示核心已进入执行阶段，真实是否开始以 attempt 的 starting／active／unknown 分开描述。task 的暂停、阻塞和对账是附加控制状态，不通过改成 pending 掩盖已经发生的工作。

中间产物可在任务仍 running 时提交并单独验收。下游只在其明确要求的产物版本验收有效时解锁，不能由上游聊天结论或原生 completed 解锁。

领取执行段只建立归属；每项任务均需 startTask。启动时把有效验收、权限、资源、并发额度、暂停状态和输入版本一起检查。输入版本变化或授权撤销后，未启动许可失效；已启动活动进入协调，不能假定瞬时撤销了外部操作。

## 4 模块接口

### 4.1 规划核心

| 操作 | 输入 | 输出 | 副作用 |
|---|---|---|---|
| validateGraph | 任务图与规则版本 | 诊断、有效子图或阻断原因 | 无 |
| plan | 状态快照、执行者、策略、估计 | 候选 Plan | 无 |
| replan | 新快照、旧 Plan、变更事件 | 影响范围、新 Plan、变更理由 | 无 |
| explain | 快照、计划、task/segment ID | 排序、阻塞和融合解释 | 无 |

不可解析的关键字段阻止规划。局部坏图是否允许无关任务推进必须由显式策略决定，默认不静默忽略错误节点。

### 4.2 调配器业务命令

| 操作 | 主要输入 | 检查与结果 |
|---|---|---|
| publishPlan | planId、basedOnRevision、epoch | 发布权、计划新鲜度、硬约束；返回新 revision |
| claimSegment | segmentId、executorId | 归属、能力、段入口条件；不提前锁定未来资源 |
| startTask | segmentId、taskId、inputVersions | 原子检查和创建 attempt、permit、resource claims、dispatch record |
| acknowledgeStart | dispatchId、permitId、executor confirmation | 核实绑定后置 active；旧 permit 拒绝 |
| submitDelivery | attemptId、artifactRefs、inputVersions | 保存交付；不自动接受 |
| recordVerdict | subjectRef、versions、policyRevision、decision、evidence | 验收身份、版本和规则一致；更新有效验收 |
| reportFailure／reportBlocked | attemptId、原因、证据 | 保留历史，触发重算或协调 |
| requestRetry | taskId、reason、budgetRef | 检查预算、熔断和输入；创建下一次尝试资格 |
| requestPause／requestCancel | scope、reason | 阻止新启动；对活动任务登记停止请求 |
| confirmStopped | attemptId、宿主证据 | 确认后释放资源；不以租约超时替代证据 |
| proposeChange／applyChange | 目标、输入或策略变更、影响范围 | 角色和版本检查；使相关许可或证据失效 |
| grant／revokeAuthorization | 动作、范围、额度、有效期 | 仅受信任授权入口；执行者消息不能自授权 |
| takeOverCoordinator | expectedEpoch、身份 | 原子递增 epoch，拒绝旧发布者后续写入 |
| reconcile | 未结束尝试、宿主观测 | 分类为继续、已终止、需重发或 unknown；不盲目重发 |

### 4.3 持久化契约

readSnapshot 返回已提交快照；commit 接收 expectedRevision、commandId、业务变更、历史和待投递记录，成功后返回 durable revision。subscribeChanges 可只返回 revision 通知，调用方自行重新读快照。

进程崩溃恢复后只能看到一次提交之前或之后的完整状态，不能出现“已启动但无资源占用记录”。幂等重复不增加业务历史和预算；显式重试是新 attempt。迁移失败保留原文件并只读；关键字段缺失不补默认值。

第一版一个项目一个持久写入者。跨进程写协调与存储后端不是已实现能力，不依赖整文件 last-write-wins 保证安全。

### 4.4 宿主适配契约

| 操作 | 业务作用 | 能力不足时 |
|---|---|---|
| capabilities | 报告成员创建、恢复、消息、观测、中断和调用身份要求 | 返回 explicit unknown／unsupported |
| ensureExecutor | 绑定或创建专项会话并返回宿主引用 | 不偷偷复用别的项目或已有普通会话 |
| deliver | 发送含委托 ID 和许可引用的消息 | 返回 accepted／rejected／unknown，不承诺已执行 |
| observe | 查询成员状态、收据和执行确认 | 带时间戳和可信度；沉默不等于停止 |
| requestInterrupt | 请求停止目标执行者 | 返回 requested／unsupported；后续等待确认 |
| reconcileDispatch | 根据业务 ID 与宿主证据对账 | 无充分证据则 unknown，暂停人工处理 |

业务调用映射到 agent-team 公开服务，真实 caller 由 agent-scoped 上下文获得。live Agent 不跨持久化、进程或不受控生命周期缓存。第二调度对话不自动获得原生 Lead 权限，实际执行能力须通过合法宿主上下文或明确接管提供。

宿主 deliver 未提供原生幂等时，外部副作用不能与 commit 原子化。业务幂等可防本地重复，不等于投递恰好一次；接收方也须核对 permit/dispatchId。

### 4.5 可视化与消息接口

GraphView 包含 stateRevision、planId、planBasedOnRevision、nodes、edges、segments、blockers、executorObservations、lastUpdated、syncStatus。宿主观测有独立 observedAt，不伪装成与核心同时提交。通知丢失或 revision 跳跃后读完整快照。

消息包含 messageId、taskId、attemptId、sender、target、kind、summary、evidenceRefs、correlationId。kind 包括 assignment、summary、blocked、failure、delivery_notice 和 change_request。长度与速率阈值在阶段 S0 冻结。

同 messageId 同内容返回既有收据，不再次发送；同 ID 不同内容报冲突。不同任务的相同文字是不同消息。重复故障可合并计数并升级，首次故障可保留专用额度，但不能无限免限频。送达和处理分别记录，消息正文不直接授予权限。

## 5 错误与事件

主要错误：INVALID_GRAPH、MISSING_INPUT、STALE_PLAN、REVISION_CONFLICT、DEPENDENCY_UNACCEPTED、RESOURCE_BUSY、UNAUTHORIZED、BUDGET_EXCEEDED、EXECUTOR_UNAVAILABLE、UNSUPPORTED_CAPABILITY、DISPATCH_UNKNOWN、STATE_UNRECOVERABLE。

主要历史事件：PlanPublished、SegmentClaimed、PermitIssued、DispatchAccepted、ExecutionConfirmed、DeliverySubmitted、VerdictRecorded、AttemptFailed、TaskInvalidated、AuthorizationChanged、PauseRequested、StopConfirmed、CoordinatorTakenOver、ProjectionLagDetected。

事件记录 causationId，重复事件按业务身份去重；乱序事件先检查所属 attempt、版本与终态，无法应用时进入待对账，不倒退覆盖较新事实。旧尝试的迟到报告可以保留为历史，不能解锁新尝试的下游。

## 6 设计验收示例

这些是未来验收用例描述，本轮不执行：

1. A 的产物已提交但未验收，B 的 claim/start 被拒绝并说明所需 verdict。
2. A 的接口产物先验收，依赖该接口的测试准备可启动；A 的其他任务继续运行。
3. 两执行者同时请求同一写资源，仅一个得到有效许可。
4. 相同 commandId 重复提交交付只产生一次记录；不同 attempt 的相同文本均保留。
5. 权威提交成功而 UI 通知失败，核心任务不回退；重连后按 revision 重建图。
6. 投递响应丢失，没有可验证执行确认时保持 unknown，不再发第二份委托。
7. 用户直接改变任务目标，形成 change request 并复核许可；聊天本身不自动验收。
