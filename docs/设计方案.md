# 设计方案

版本：0.2 草案。日期：2026-10-20。简化方向已确认，具体契约待评审；本文不是运行能力证明。

## 1 产品结构与首版范围

项目是 DeepSeek Harness 优先的多 Agent 开发测试协作插件。用户保留 1—2 个调度对话和多个长期专项执行对话，减少调度对话承载的背景、执行轨迹和重复转述。

首版复用 agent-team 的成员创建、查询、冷恢复、消息与中断能力，自建任务、依赖、执行段、验收、资源和历史状态。关于宿主的新增能力来自用户提供的源码调查，尚未运行验收，见 [Harness 接入证据](Harness接入证据.md)。

**不使用原生任务板进行调度，不维护双板镜像，不设置原生 gate 任务。** 任务 ID 由核心生成，平台绑定独立保存。headless、跨 Team、跨进程、复用任意既有 GUI 会话均为后续备选。

一个调度对话持有当前计划发布权，第二个可审阅或显式接管。其余对话按开发、测试、接口或联调职责复用。teammate 即使在宿主中是 continuable child，也不意味着完整轨迹需要回灌 Lead；是否降低上下文压力以实测为准。

首版目标是单宿主进程、单团队范围内的协调。一个进程可以并发运行多个 Agent；具体能力与限额需验证。核心可内嵌于插件，不必另起服务。语言、数据库、图布局库和插件安装形式尚未冻结。

## 2 模块职责和数据流

| 模块 | 输入 | 输出与责任 | 边界 |
|---|---|---|---|
| 调度算法 | 任务图、状态快照、执行者、策略和估计 | 诊断、排序、候选执行段、中间交付点、停止与解锁条件、选择理由 | 无副作用，不派发，不修改事实 |
| 调配器 | 候选计划、用户命令、执行事件、验收与授权 | 发布计划、认领、逐任务许可、资源仲裁、消息投递、恢复和重算触发 | 所有业务写入的唯一入口 |
| ScheduleStore | 调配器验证后的事务 | 权威状态、历史、幂等记录和待投递记录 | 可靠提交，不依据 UI 或原生任务状态回写事实 |
| Harness 适配器 | 核心委托、可信调用者与宿主事件 | 公开 agent-team 服务调用、身份绑定、能力报告和归一化事件 | 不绕过角色、授权和接管条件 |
| 可视化流程图 | 核心带版本快照及单独标识的宿主观测 | 图、泳道、任务详情、阻塞解释、操作意图 | 不是第二份任务数据库 |
| 随附 Skill | 工具和流程说明 | 指导查询、领取、交付及异常报告 | 不代替门禁程序 |

正常流程：生成候选计划 → 发布 → 认领执行段 → 为当前任务核发许可 → 投递委托并确认 → 提交交付 → 指定验收者裁决 → 解锁与重算 → 刷新视图。

接口和字段见 [接口与数据契约](接口与数据契约.md)。所有产品内部 ID 与宿主 session ID 分开；宿主引用只存在于适配器绑定中。导出通用任务图不需要携带 Harness 内部对象。

## 3 可视化任务流程图

图必须回答：什么能做、谁在做、为什么停住、谁交付什么后能继续、当前执行段在哪里结束，以及计划为什么改变。

- 默认任务依赖图，可按职责或执行者分组；折叠后仍保留跨组依赖提示。
- 原子任务保留独立 ID；执行段以边界或路径显示，不能合成一个无法追溯的节点。
- 硬前置、软依赖、接口约定和模拟输入采用线型、文字及颜色共同区分。
- 实际状态和预测排程分开；未知时长不显示为零，等待激活不显示为运行中。
- 展示中间产物的待提交、待验收、已验收和失效状态。
- 节点详情包含输入输出、验收规则、尝试历史、资源声明、证据版本、停止及下一解锁条件。
- 提供搜索、缩放、上下游聚焦、阻塞筛选和执行段展开。
- 显示 snapshot revision、最后观测时间和同步状态；过期视图不能直接提交无版本检查的修改。
- 用户点击发布、认领、暂停、验收等，只提交命令；收到核心确认后再展示操作成功。

参考 Archify 的结构化图输入、关系解释、图例和可探索布局。首版不要求动画或视频导出，不预定引入 Archify 代码。

首选自建面板，以核心快照为任务数据源，成员 roster 从适配器读取并附观测时间。可通过支持的 session projection 或其他公开 UI 接口传输；采用推送或 waitForChange 加快照刷新均可。通知只代表可能有变化，不假定含完整增量。

持久状态已提交但通知失败时显示“视图待同步”，重连读取完整快照。镜像事件、投影检查点和缓存可重建，不承担验收或资源权威。若使用 ignorable 事件，仅传可丢弃的展示通知；不把可忽略事件作为唯一账本，不默认每次追加完整状态。

## 4 调度算法

### 4.1 约束优先与排序

先满足验收依赖、授权、资源互斥、能力、负责人约定和并发限额，再优化效率。不能用工期收益抵消约束违规。

首版采用可解释启发式：考虑剩余关键路径、下游解锁价值、执行者预计完成时间、上下文连续性、交接开销和风险。权重、估计方法和融合上限在实现前冻结；相同输入、策略版本和随机种子应可复现。并列时采用稳定 ID 顺序。未知耗时保留区间或 unknown，不伪造精确关键路径。

### 4.2 规划流程

1. 规范化任务与验收规则，检查 ID、字段、引用和未知项。
2. 建立带类型关系图。硬前置形成可执行 DAG；软关系环不直接视为死锁。
3. 诊断循环、缺失输入、不可能满足的能力和资源要求，返回相关节点与原因。
4. 用实际已验收事实计算就绪边界，同时输出其他阻塞条件。
5. 在符合硬约束的候选中排序，评估复用或新增执行者的成本。
6. 推演执行段和资源时间安排，保留段内每个任务的启动条件。
7. 标明应提前交付的产物、停止条件、下一解锁条件和被排除任务的原因。
8. 返回基于某 revision 的候选计划；实际发布与启动时重新检查。

模拟输入只能解锁明确允许它的任务，如测试准备；不得替代真实集成验收。接口约定是一类产物，是否构成硬前置须显式指定，不能从类别名推断。

### 4.3 执行段融合

同一执行者能够连续推进、上下文相容且不延迟必要交付的任务可以合并委托。任务数量、估计时长、上下文预算、风险与回退成本共同限制段长。

例如 A1 → A2 → 等待 B3 → A3 → A4：B3 未验收时，当前可发布段止于 A2；A3、A4 可出现在预测计划，但没有实际执行许可。B3 验收后重算。

若 A1 的接口产物可解锁 B1，应立即提交并按规则验收，不等 A2 结束才发布。A 对话可以继续其他已获许可工作。若段内下一步依赖外部验收且无其他工作，该等待可能成为段边界。

段内每个原子任务启动前仍检查前置、资源、权限和预算。完成一段不关闭对话；后续复用同一上下文，不将“执行段”误当成“会话生命周期”。

### 4.4 动态重算与上下文

交付、验收、失败、授权变化、容量变化及新增任务触发影响分析。影响范围包括依赖后继、计分祖先、资源竞争者和执行者占用，不仅是直接子节点。

通常局部重算；影响边界无法可靠界定时允许全量重算。运行任务默认固定，撤销须先协调；不能直接换计划让同一资源出现第二个写者。输入产物失效时标记受影响结果需复核，保留原证据。

优先复用职责相符的专项对话，再建议新建。新增对话需要有可并行任务，并说明收益、重复背景和管理成本。上下文交接只传相关约定、产物和失败摘要，不复制全部历史。压缩事件无法观测时使用明确标注的代理指标，不声称压缩次数已减少。

## 5 调配器与门禁

### 5.1 执行前许可

发布计划不等于认领，认领不等于启动，启动不等于交付，交付不等于验收。

认领确定执行段归属；startTask 在单个提交中检查前置验收、角色、执行者容量、资源、授权和暂停状态，并记录 attempt、许可和待投递委托。依赖未满足时不发许可。验收只允许规则指定的人类、检查器或执行角色，默认不允许执行者自行盖章。

许可约束参与本插件的协作路径，不是任意代码执行的安全边界。未登记工具或人工编辑仍可能修改文件；必须明确宿主沙箱、插件流程门禁和声明式资源锁的不同保证。

### 5.2 单一状态与持久化

ScheduleStore 自建稳定 ID，不关联原生 task revision，不双写原生任务板。核心状态至少包含任务、产物、执行段、运行尝试、验收、授权、资源、计划、幂等与待投递记录。

首版每个项目只允许一个持久写入者，业务写入按序执行并带 revision 检查；第二实例只能拒绝写入或以只读方式连接。底层存储必须支持可靠提交与恢复，不能仅因 ctx.storage 可用就认定满足要求。具体存储后端在设计评审中选择。

关键字段缺失、损坏或未知高版本进入只读诊断，不补默认值继续执行。迁移前留存原状态，迁移失败不覆盖原文件。核心事实、历史与幂等记录应在同一提交边界内持久化。

### 5.3 资源与停止

资源以规范化标识和 read/write 模式声明；同一文件不同片段默认仍冲突。首版不宣称提供 worktree 隔离。资源在当前任务需要时取得，不提前锁住整段所有未来资源。

lease 超时仅说明失联，不证明执行已停止。中断请求被接受也不等于工具进程已退出；确认停止或人工对账前，冲突资源保留占用。直接调用原生中断应经包装登记状态，不让核心遗漏这项变更。

第二调度对话接管时递增发布权 epoch，旧发布者写入被拒绝。暂停后拒绝新启动；正在执行的活动按已验证的宿主中断能力处理，结果未知则明确标记。

### 5.4 投递与恢复

核心先提交委托和待投递记录，再调用宿主。记录“待投递、已送达、执行者已确认、结果未知、失败”等不同状态；宿主 messageId 不代表接收方已处理。

宿主调用与核心提交不构成同一事务。调用超时或进程崩溃后，先通过运行 ID、委托 ID和执行者确认对账。宿主无幂等支持时，不承诺恰好执行一次；不能安全判定就暂停并请求处理，而非盲目重发。

重启时恢复未结束尝试、资源和待投递状态，再对账成员。没有 live Agent 调用上下文时先只读，等待宿主恢复，而非偷偷新建替代会话。

### 5.5 消息与人工介入

消息携带 taskId、attemptId、messageId 和类型；去重以业务身份为准，同键不同内容报冲突，不凭相同文本删除不同任务报告。限制大小和发送速率；普通进展可合并，错误保留首次通知、重复次数和升级信息，不无限豁免限频。

消息工具包装负责约束公开给执行者的通道；其他插件直调服务等旁路需列入宿主能力边界。摘要默认只含结论、阻塞、证据引用和需要决策的事项，不能把全文当作必要摘要。

用户在专项对话直接说话属于正常交互。涉及目标、输入、权限或资源变化时登记 change request；对相关许可暂停或重新确认。用户普通聊天不自动构成验收、预算增加或权限升级，也无需全量回传 Lead。

## 6 开发测试闭环

接口约定验收 → 开发与测试准备并行 → 模块交付 → 针对性验证 → 缺陷关联修复 → 受影响回归 → 集成验收。

验收绑定输入和产物版本、检查规则及环境。有效旧证据可以复用，相关变更才使其失效。模拟输入、静态检查、本地运行、宿主联调和真实模型分别记账，不能互相冒充。

重试增加 attempt，但保留失败历史、累计预算和熔断计数；换执行者或融合执行段不清零。适用项目有更具体预算和停止规则时应作为约束导入。

## 7 适配边界和设计待决项

首版通过公开 agentTeams 成员与通信服务接入，不依赖 internal，不暴露原生任务写工具。成员查询可复用，任务查询必须读取核心；创建、消息和中断工具经过核心协调。具体工具名待核查，当前名称仅为业务契约。

UI 只使用自建任务视图，可复用 roster 数据；不要求官方面板承担第二套任务展示。上游工具和提示词协议不同，应设计兼容包装或同步更新说明，不能假设改同名工具后模型一定正确调用。

在进入实现前需确定：数据 schema、存储提交方式、权限角色、默认段长和消息预算、算法计分策略、性能与刷新阈值、目标宿主版本及包解析路径。其他平台通过能力声明适配，不支持的操作返回 unsupported，禁止静默降级。

详细验收和待办见 [阶段验收与评测](阶段验收与评测.md) 与 [任务清单](任务清单.md)。本轮不写代码、不改 DSH 配置、不运行测试。
