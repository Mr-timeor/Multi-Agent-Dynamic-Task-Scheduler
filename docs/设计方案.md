# 设计方案

2026-10-24同步当前实现。方向不变：agent-team承载专项会话、自建权威状态、不用原生板、图从核心派生。算法细节见[调度算法](调度算法.md)。

## 三部分职责

| 部分 | 当前实现 | 接口 |
|---|---|---|
| 算法 | 硬前置DAG、就绪集、优先级／下游解锁排序、资源冲突贪心分配、顺序段融合 | normalize、diagnose、plan |
| 调配器 | 文件保存、当前任务占用、一次投递、回执、提交、可选验收和对账 | Scheduler与FileStore |
| 可视化 | 竖向拓扑分层SVG（阶段自上而下、同阶段按类别分组）、节点卡片详情、等待原因、段和交付点列表、搜索缩放 | renderGraph |

Harness适配层负责合法调用者、成员创建和消息发送。核心不导入宿主包；一个Lead绑定一个团队，多视图只有读取能力。

## 执行方式

规划沿当前可连续完成的任务形成执行段。遇到外部前置、review检查点或段长上限停止。预测不修改状态，未来任务不提前占用资源。

默认手动模式首次由Lead派发；开启autoDispatch后，首次next可直接领取就绪任务，交付会触发给等待成员的委托。专项执行者完成当前任务后再next领取，不要求Lead逐项转述。中间产物及时提交，普通产物直接接受，明确声明review的产物才等待验收。

所有真实开始都重新检查依赖、授权、执行者和资源。运行记录保存结果与失败。文件／目录声明做粗粒度冲突判断；共享工作区没有文件系统隔离。

## 最小选择

TypeScript编译为ESM；单宿主进程；JSON快照；默认段长4、回执等待120秒。没有epoch、租约、接管、发布握手、独立Permit实体或全量哈希失效机制。

模型调用只有4个入口，内部ID由程序处理。默认不要求人类检查每个小任务；review和approval只用于明确设置的节点。

当前算法不估计LLM耗时、不实现HEFT或局部增量重算。只读图输出独立HTML，并已接入宿主文件预览和自动刷新，不另建庞大界面框架。

## 当前限制

真实宿主加载、原生图预览、模型开发测试闭环和依赖解除后自动唤醒均已通过相应验收；图已提供职责泳道、执行段展示、搜索/缩放与状态跟随。真实效率、费用和上下文压缩收益仍未证明。当前图只读，单实例单项目/Lead，资源声明不提供文件系统隔离，重启后的未结束运行需要对账。

软依赖、mock输入语义、自动上下文重建与跨进程恢复后置。Lead日志scheduler/*存储候选不阻塞现有文件方案。
