```text

```

三个成员各自是fresh上下文的专项会话；只返回摘要和产物引用，Lead不接收全文转述。

| 实际交付事件 | 继续方式 |
|---|---|
| P1交付contract | 核心next继续D1；Lead分别dispatch CLI和QA，启动C1/Q1 |
| D1/C1/Q1全部完成 | QA可next领Q2；如果已waiting停下，Lead dispatch QA |
| Q2首轮报告完成 | 核心和CLI分别next领D2/C2；已停下的由Lead分别dispatch唤醒 |
| D2/C2全部完成 | QA next领Q3；已停下则Lead dispatch QA |
| Q3真实通过 | CLI next领C3；已停下则Lead dispatch CLI |
| Q3失败或任务blocked/unknown | 保留现场，记录原因，停止扩大试用 |

只能在依赖实际满足后派发。不要为了凑并行而暂停执行者；没有重叠就记录没有。Lead仅在新交付或需要处理阻断时查询一次，不持续status轮询。成员next返回waiting即结束回合；当前插件没有自动唤醒等待成员的机制，所有重新派发及用户唤醒均计入观察。

## 首轮失败怎样处理

Q2是“运行并发布首轮报告”的任务，报告必须写明实际功能测试失败。即使Node测试非零，只要真实命令及缺陷报告完整，Q2可以completed，解锁已有的D2/C2。这是预先安排的缺陷处理路径，不能写成首轮功能通过。

D2/C2读取同一报告、各改自己文件。无缺陷写无需修改，不故意留错或制造故障。Q3才是最终功能验收，非零或smoke不符必须failed/blocked，C3保持未解锁。调度状态、报告结论与原始命令结果分别记录。若最终失败，本轮到此交付，不临时绕过前置、不把accepted报告清掉再retry。

其他实现任务failed/blocked时先报告具体阻断，不自动构造无限修复链。unknown不自动重发，先核对成员和run；同一操作没有新信息/状态变化就停止重复。这里没有全局自动循环检测器，行为规则须由Lead和成员遵守。
