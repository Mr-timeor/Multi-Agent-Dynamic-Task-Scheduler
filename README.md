# Multi-Agent Dynamic Task Scheduler

面向 DeepSeek Harness 的依赖感知任务规划与执行段调度插件。

**当前阶段：0.2 设计草案，尚未进入实现。** 简化架构已由用户确认；具体接口、存储和验收阈值仍需评审。本轮产物是项目说明、模块设计、接口契约与验收计划；不包含插件、算法程序或可运行的流程图。

## 项目要解决的问题

多对话开发中，任务切分过碎、跨职责依赖不清晰、调度对话承担过多背景和转述，容易产生等待、重复阅读、重复验证与交接。不断增加对话数量并不能自动解决这些问题。

本项目围绕开发和测试流程，让少量调度对话协调多个专项执行对话。在依赖、资源、上下文和授权约束下，提高有效并行推进量，减少总完成时间、阻塞、返工与调度介入。

多开对话的另一个目的，是分散不同职责的上下文，减少单个对话的信息混杂、记忆压缩及压缩后的背景恢复成本。这个效果需要实测，不能由对话数量直接推导。

## 已确认的方向

- 名称使用当前文件夹名：**Multi-Agent Dynamic Task Scheduler**。
- DeepSeek Harness 插件优先，核心的数据模型和调度逻辑保持平台独立。
- 面向开发、测试、联调、缺陷修复与回归验证。
- 保留 1—2 个调度对话，其他对话围绕稳定职责专项化。
- 三个主要组成部分是可视化任务流程图、调度算法、调配器。
- 复用 agent-team 的成员生命周期与消息通道，自建唯一权威调度状态；首版不维护原生任务板镜像、不设置原生闸门任务。
- 按“问题与契约设计 → 合成验证 → Harness 接入验证 → 插件试用”推进。
- AIC 不属于实施对象，不读取或修改它的源码、任务集、账本和案例材料。
- 仓库创建、公开与否、项目许可证尚未决定；当前不创建或发布远程仓库。

## Harness 接入方向

首版以 **agent-team 持久专项会话** 为接入候选，复用成员创建、恢复、查询、中断和消息能力。完整执行轨迹留在执行者自己的会话里，调度对话只接收受控摘要与异常。成员在宿主中属于子会话，不等于全部轨迹必须回灌 Lead。

这一能力判断主要来自用户提供的 DS 源码核查报告，尚未独立复核和运行验收。此前本地直接核查的 headless 能力保留为后续备选，不再作为首版前置。详见 [Harness 接入证据](docs/Harness接入证据.md)。

目标流程：

1. 调度对话生成候选计划，调配器发布到本插件的权威状态。
2. 专项会话认领执行段；每个原子任务开始前重新检查依赖验收、资源与授权。
3. 适配器通过 agent-team 消息通道送达委托，收集执行者确认与交付。
4. 指定验收者或检查器提交有效结论，调配器更新状态并解锁下游。
5. 流程图从同一状态派生，显示实际执行、预测安排、阻塞与下一解锁条件。

原生任务板不负责认领、完成或解锁，也不与核心双写。headless、任意已有 GUI 会话接管、跨 Team 协调和跨进程执行不属于首版承诺。

单进程可以支持并发，但实际并发度仍待验证。共享工作目录的资源约束由调配器管理，它不能替代宿主沙箱或阻止协议外的文件修改。用户直接介入专项对话是正常操作，影响计划的变更需登记，不能自动视为验收通过。

## 三个组成部分

| 部分 | 核心职责 | 不承担的职责 |
|---|---|---|
| 可视化任务流程图 | 展示任务依赖、执行段、专项对话、交付点、实际状态与阻塞原因 | 不独立保存事实，不通过修改图形直接宣布验收完成 |
| 调度算法 | 检查依赖和约束，排序、分配候选执行者、融合执行段，解释选择 | 不调用模型、不启动对话、不授予权限、不把预测写成实际完成 |
| 调配器 | 管理任务状态、计划发布、认领、资源占用、交付、验收记录和重算触发 | 不假设具备跨对话通信，不替用户批准费用或不可逆操作 |

三者使用同一个带版本的项目状态。Skill 可以作为插件随附的操作指引，但不能代替程序里的状态检查与约束执行。

## 对话与任务的关系

| 概念 | 含义 |
|---|---|
| 类别 | 稳定业务或责任划分，例如后端、前端、测试；不是一次派发的任务包 |
| 原子任务 | 有明确输入、输出和验收条件的最小规划节点 |
| 执行段 | 某个执行者在一次委托下可以连续推进的任务集合及内部顺序 |
| 专项对话 | 承载独立持久工作上下文；首版拟由 agent-team teammate 实现，可先后承担多个执行段 |
| 中间交付点 | 发布并验收某项产物后可解锁其他任务，本对话可继续当前执行段 |
| 外部阻断 | 当前执行段无法自行解除的依赖、资源、授权或外部输入限制 |

一个执行段结束，不代表必须关闭或新建对话；对话长期存在，也不代表始终占用资源或一直可运行。专项对话、临时子 Agent、运行进程和底层模型需要分别建模。
